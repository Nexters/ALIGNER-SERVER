# 리뷰 루브릭

> 정책 정본은 `CONTRIBUTING.md` §5다.

## 무엇에 시간을 쓰는가

포맷·스타일은 **Ktlint**가, 계층 규칙 대부분은 **컨벤션 플러그인**이 이미 막는다.
**도구가 못 잡는 것**에만 리뷰 시간을 쓴다. 다음 순서로 본다.

1. **`build.gradle.kts` 의존성 추가** — 가장 중요하다.
   도구가 못 막는 유일한 아키텍처 위반 지점이다(`docs/architecture.md` §8).
   빌드 파일이 바뀐 변경은 **이 항목부터** 본다. 상세 체크는 `harness/rules/architecture.md`.
2. **코드가 놓인 계층** — 비즈니스 판단이 `api`에, DB 관심사가 `service`에 샜는지.
3. **도메인 용어** — AGENTS.md §2 용어집과 다른 이름을 새로 만들었는지.
4. **테스트가 의미 있는지** — 통과만 하는 테스트인지, 깨지면 진짜 문제를 알려주는지.
5. **Bean 등록 누락** — 컨트롤러 `@Bean` 등록, `AutoConfiguration.imports`.
   빌드도 기동도 되는데 호출만 404가 되는 자리라 사람 눈으로만 잡힌다.
6. **하드코딩** — 스크리닝 문항·원인 매핑·자세 포인트가 코드에 박혔는지.

## 코멘트 접두사

| 접두사 | 뜻 | 쓰는 곳 |
| --- | --- | --- |
| `[필수]` | 고쳐야 병합 가능 | 버그, 아키텍처 위반, 용어 불일치, 시크릿 노출 |
| `[제안]` | 반영해도 좋고 안 해도 됨 | 취향, 대안, 리팩터링 아이디어 |
| `[질문]` | 이해가 안 돼서 묻는 것 | 의도 확인 |

- **취향 차이는 전부 `[제안]`이다.** `[필수]`를 남발하면 접두사가 의미를 잃는다.
- `[제안]`만 남았다면 작성자 판단으로 병합해도 된다.
- "왜 이렇게 했어요?"보다 **"이 경우엔 X가 되지 않나요?"**로 쓴다. 사람이 아니라 코드를 본다.

## 코멘트 작성 형식

```
[필수] {domain}/api/CourseController.kt:42

원인 판별 분기가 컨트롤러에 있습니다. docs/architecture.md §3 기준으로
비즈니스 판단은 service 계층입니다. CourseCommandService로 옮기면
스크리닝 감수 결과가 바뀔 때 고칠 자리도 한 곳이 됩니다.
```

- 파일:라인을 반드시 붙인다.
- 근거로 문서 절 번호(`docs/architecture.md §N`, `AGENTS.md §N`)를 댄다. "제 생각엔"으로 끝내지 않는다.
- 고치는 방법까지 한 줄 적는다. 지적만 남기지 않는다.

## 결과 정리 형식

1. 한 줄 총평 (병합 가능 / `[필수]` N건 있음)
2. `[필수]` → `[제안]` → `[질문]` 순으로 나열
3. **못 본 것**을 마지막에 명시 — 실행하지 못한 검증, 확인 못 한 범위

문제가 없으면 그렇게 말한다. 억지로 지적을 만들지 않는다.
대신 **남은 테스트 공백이나 잔여 위험**은 짧게 적는다.

## 의견이 갈릴 때

**되돌리기 비용**으로 판단한다.

- 되돌리기 쉬운 것(구현 방식, 네이밍 디테일) → **작성자 뜻대로**
- 되돌리기 비싼 것(모듈 경계, DB 스키마, API 스펙, 의존성 추가) → **합의하고 간다**

합의가 안 되면 PR에서 끌지 말고 허들로 옮기자고 제안한다.
