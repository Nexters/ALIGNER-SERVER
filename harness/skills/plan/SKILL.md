# 기획 — 요구사항을 이슈로

파이프라인의 첫 단계다. **무엇을 만들지 확정하고 GitHub 이슈로 남기는 것**이 산출물이다.
이슈 번호가 있어야 브랜치를 팔 수 있으므로(`CONTRIBUTING.md` §1), 여기서 멈추면 다음이 없다.

## 1. 범위 판정 — 가장 먼저 한다

`AGENTS.md` §3을 읽고 요청을 셋 중 하나로 분류한다.

| 판정 | 조건 | 행동 |
| --- | --- | --- |
| **P0** | MVP 8개 기능 중 하나에 해당 | 진행 |
| **P1** | §3 하단 "지금 만들지 말 것" 목록에 있음 | **구현하지 않는다.** 사용자에게 P1임을 알리고, 원하면 백로그 이슈만 만든다 |
| **판단 불가** | 어느 쪽인지 모호 | 사용자에게 묻는다. 임의로 P0로 끌어올리지 않는다 |

P1 목록: 고민 유형 1탭, 사후 사진·영상 분석, 전후 비교 아카이브, 배지·리워드,
이력 리마인드, 푸시 알림, 통증→전문가 라우팅, 외부 앱 기록 통합,
스텝별 통과 테스트·잠금해제, 근거·전문가 감수 보기.

## 2. 배경 확인

요청의 근거가 기획에 있는지 확인한다. 자세한 사용자 리서치·IA가 필요하면
**`context-researcher` 서브에이전트**에 맡긴다 (`docs/context/user-research-insights.md`는 길다).

핵심 도메인 루프(`AGENTS.md` §2)의 어느 단계에 해당하는지 짚는다.
특히 **⑦ 미달 포인트 → 보강 동작 자동 편성**은 이 서비스의 리텐션 엔진이므로
단순 CRUD로 축소되지 않았는지 본다.

## 3. 이슈 초안 작성

`.github/ISSUE_TEMPLATE/`의 템플릿 3종 중 맞는 것을 읽고 그 구조를 채운다.

| 템플릿 | 라벨 | 쓰는 때 |
| --- | --- | --- |
| `feature.yml` | `feature` | 새 기능 |
| `bug.yml` | `bug` | 버그 |
| `task.yml` | `chore` | 설정·문서·리팩터링 |

작성 원칙:

- **한글로 쓴다.**
- 도메인 용어는 `AGENTS.md` §2 용어집을 그대로 쓴다. 임의 영문 번역을 만들지 않는다.
- 완료 조건을 **검증 가능한 문장**으로 쓴다. "잘 동작한다"가 아니라
  "스크리닝 응답 2개를 보내면 원인 코드와 코스 ID가 응답에 포함된다".
- 이슈 하나는 PR 하나 크기로 자른다. 커지면 나눠서 여러 이슈로 만든다.
- **구현 방법을 이슈에 못 박지 않는다.** 그건 `/design`의 몫이다.
  다만 어느 도메인/계층인지 감이 잡혔으면 한 줄 메모로 남긴다.

## 4. 등록

초안을 사용자에게 보여주고 **승인을 받은 뒤** 등록한다. 확인 없이 이슈를 만들지 않는다.

```bash
gh issue create --title "<제목>" --body-file <파일> --label <라벨>
```

`gh`가 없으면 (`gh: command not found`) 본문을 파일로 저장해 경로를 알려주고,
`brew install gh && gh auth login`을 안내한다. 다른 방법을 찾아 우회하지 않는다.

저장소: https://github.com/Nexters/ALIGNER-SERVER

## 5. 다음 단계 안내

이슈 번호를 확인한 뒤 사용자에게 알린다.

```
이슈 #12 생성됨 → 다음은 /design 12 (설계) 또는 /flow 12 (끝까지 자동 진행)
```
