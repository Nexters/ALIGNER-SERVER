# 커밋

절차와 컨벤션은 `harness/rules/git-workflow.md`가 정본이다.

## 1. 브랜치 확인 — 가장 먼저

```bash
git branch --show-current
```

**`main`·`develop`이면 커밋하지 않는다.** 사용자에게 알리고 작업 브랜치를 만들지 묻는다.
(푸시는 훅이 막지만, 커밋 자체를 여기서 막는 게 낫다.)

## 2. 변경 확인

```bash
git status --short
git diff
```

- **시크릿 확인** — `.env`, `application-local.yml`, `*.key`, `*.jks`, 카카오 앱 키,
  DB 비밀번호, JWT 시크릿이 섞였는지 본다. 있으면 커밋을 멈추고 사용자에게 알린다.
- 의도하지 않은 파일(빌드 산출물, IDE 설정, 스크래치 파일)이 섞였는지 본다.

## 3. 커밋 단위 자르기

**하나의 커밋은 하나의 목적만 담는다.** 변경에 목적이 둘 이상이면 나눈다.

예 — 아래는 두 커밋이다.

```
feat: 카카오 소셜 로그인 API 추가
chore: ktlint 설정 추가
```

`git add .`로 뭉뚱그리지 않는다. 목적별로 파일을 골라 스테이징한다.

## 4. 메시지 작성

```
<type>: <한글 요약>
```

- type: `feat` `fix` `refactor` `test` `docs` `chore` `ci` `style` `perf`
- **브랜치 접두사는 `feature/`, 커밋 타입은 `feat`다.** 헷갈리는 자리다.
- 제목은 한글, 마침표 없이, 명사형 또는 `~추가/수정/삭제`.
- 본문은 필요할 때만. 쓴다면 **무엇이 아니라 왜**를 쓴다.

```
refactor: 코스 처방 로직을 도메인 서비스로 분리

컨트롤러에 있던 원인 판별 분기를 CoursePrescriber로 옮겼다.
스크리닝 응답 → 원인 매핑이 한 곳에 모여 감수 결과 반영이 쉬워진다.
```

## 5. 실행 — 사전 승인 없이 진행한다

사용자가 커밋을 지시했다면 **메시지 승인을 따로 받지 않고 바로 커밋한다.**
메시지는 커밋한 뒤 보고에서 보여준다.

```bash
git add <파일들>
git diff --staged
git commit -m "feat: 카카오 소셜 로그인 API 추가"
```

- 커밋 트레일러(`Co-Authored-By` 등)는 **넣지 않는다.** 팀 컨벤션에 없다.
- **`--no-verify`·`SKIP_HOOKS=1`을 쓰지 않는다.** `.githooks/`의 pre-commit·commit-msg가
  시크릿·보호 브랜치·메시지 컨벤션을 검사한다. 훅이 막으면 **우회하지 말고 원인을 고친다.**
- **푸시는 하지 않는다.** 푸시는 `/pr`이 한다.

### 그래도 멈추는 경우

승인 없이 진행하지만, 아래는 **커밋하지 말고 사용자에게 알린다.**

- 시크릿이 스테이징에 섞였다
- 현재 브랜치가 `main`·`develop`이다
- 변경 목적이 둘 이상인데 어떻게 나눌지 판단이 안 선다
- 커밋 훅이 실패했고 원인이 코드가 아니라 규칙 해석 문제다

## 6. 보고

커밋 해시와 메시지를 보여주고, 다음 단계(`/pr`)를 안내한다.
훅이 무엇을 검사해서 통과했는지는 굳이 적지 않는다.
